# WBD Analyzer — 페이지 분리 버전

원본 `../index.html`을 유지하면서 만든 별도 앱입니다. 배포 루트의 기존 주소는 바뀌지 않으며 새 버전의 진입점은 `/app/index.html`입니다.

## 실행

저장소 루트에서 Node.js로 실행합니다. npm 설치나 외부 패키지 설치는 필요 없습니다.

```sh
node app/scripts/serve.mjs
```

브라우저에서 `http://127.0.0.1:4173/app/`을 엽니다. 원본은 같은 서버의 `/index.html`에서 확인할 수 있습니다. ES 모듈과 데이터 요청을 사용하므로 HTML 파일을 더블 클릭하는 `file://` 실행은 지원하지 않습니다.

## 구조

```text
app/
  index.html, pitcher.html, batter.html, ...  실제 진입 문서 26개
  templates/
    shell.html               공통 메뉴·파일 업로드·모달
    pages/*.html             각 화면의 HTML 원본
  styles/
    analyzer.css             기존 스타일
    pages.css                페이지 버전의 공통 스타일
  js/
    bootstrap.js             시작·데이터 복원·저장 후 문서 이동
    core/
      routes.js              경로와 화면 이름
      runtime.js             모듈 초기화와 호환 계층
      session-store.js       IndexedDB 저장소
      view-state.js          복원 대상 상태와 입력 컨트롤
      page-controller.js     현재 화면 렌더링·상세 링크 연결
      symbols.js             기존 HTML 이벤트용 호환 심볼
    features/*.js            분석·카드·수비·스카우팅 등 기능 모듈 43개
  scripts/
    build.mjs                템플릿에서 26개 HTML 생성
    serve.mjs                로컬 전용 HTTP 서버
  tests/migration.test.mjs   원본 계산 결과와 회귀 비교
  migration.json             원본 SHA-256·페이지·함수 위치 색인
```

각 HTML에는 해당 화면의 `.page` 하나만 있습니다. 메뉴는 실제 `<a href>` 링크이며 문서가 전환됩니다. 해시만 바꾸거나 나머지 25개 화면을 숨기는 방식이 아닙니다. 공통 메뉴의 중복은 빌드 산출물에만 있고, 수정할 원본은 `templates/shell.html` 한 곳입니다.

데이터는 기존 `../data/`를 그대로 사용합니다. `<base href="../">`로 원본 데이터·로고 경로를 보존하며 GitHub Pages의 하위 저장소 경로에서도 동작합니다. 원본 manifest 생성 스크립트나 워크플로는 변경하지 않았습니다. 현재 체크아웃에 번들이 없어도 기존 개별 파일 다운로드 처리가 작동합니다.

## 수정과 빌드

- 화면: `templates/pages/<page>.html`
- 공통 메뉴: `templates/shell.html`
- 분석 및 UI 로직: `js/features/`의 해당 모듈
- 페이지 이동·저장: `js/core/`, `js/bootstrap.js`
- 디자인: `styles/`

템플릿을 수정하면 저장소 루트에서 다시 빌드합니다.

```sh
node app/scripts/build.mjs
node --test app/tests/*.test.mjs
```

JS와 CSS 수정은 빌드 없이 반영됩니다. 브라우저에서는 새로고침해야 합니다. 생성된 26개 HTML도 함께 버전 관리하면 GitHub Pages에서 별도 빌드 없이 제공할 수 있습니다. 이번 작업에서는 커밋·푸시·배포를 수행하지 않았습니다.

`../scripts/migrate-app.cjs`는 원본에서 처음 분리할 때 사용한 **일회성 이관 도구**입니다. 일반 빌드에 사용하지 않습니다. 이미 이관한 폴더에는 기본적으로 재실행을 거부하며, 강제 재추출은 이후 수정 사항을 덮어씁니다. 이관 시에만 Babel parser/traverse 또는 `--parser-bundle <babelBundle.js>`가 필요합니다. 실행·일반 빌드·테스트에는 필요 없습니다.

## 모듈과 호환성

기존 최상위 변수·함수 참조를 구문 분석기의 바인딩 정보로 `wbdContext`에 연결했습니다. 모듈 내부의 지역 변수는 유지하고 공유 상태 접근만 명시적으로 바꿨습니다. 모든 모듈의 `register(context)`를 먼저 실행한 다음 `initialize(context)`를 원래 순서대로 실행해, 함수 호이스팅과 뒤쪽 덮어쓰기의 기존 동작을 보존합니다.

기존 인라인 `onclick`과 `window.*` 확장 코드는 호환 접근자를 통해 같은 context를 사용합니다. 따라서 **전역 호환 진입점을 모두 없앤 완전한 독립 모듈 구조는 아닙니다.** 기존 계산식을 유지하면서 단계적으로 정리할 수 있도록 만든 구조입니다. 기능 모듈은 공통으로 로드하며, 화면별 코드 지연 로딩은 아직 적용하지 않았습니다. 브라우저 캐시를 사용하지만 문서 이동 시 JS 초기화와 분석 데이터 재구성은 다시 수행합니다.

## 페이지 간 상태

- 원본 경기 로그는 IndexedDB에 저장합니다. 큰 데이터를 localStorage에 넣지 않습니다.
- 이동 전에 저장 트랜잭션이 완료될 때까지 기다립니다. 저장 실패 시 현재 화면을 유지하고 오류를 표시합니다.
- 페이지 진입 시 원본 로그에서 경기를 재구성하고 기존 게임 ID와 활성 경기 범위를 복원합니다.
- 선수 선택, 투타 하위 탭, 경기 필터, 공략 대상, 일부 화면 컨트롤을 복원합니다.
- 팀 구성·즐겨찾기·별칭·테마 등은 기존 `wbd_*` localStorage 설정을 사용하므로 같은 도메인의 원본 앱과 공유합니다.
- 세션 식별자는 sessionStorage에 있어 같은 탭의 이동·새로고침을 이어 줍니다. 브라우저 저장소 삭제, 비공개 모드 정책, 탭 종료 후 재방문까지의 영구 보존은 보장하지 않습니다. 필요한 기록은 기존 내보내기 기능으로 백업할 수 있습니다.
- 첫 방문은 기존처럼 서버 데이터를 자동으로 불러오며, 저장 세션이 있으면 같은 데이터를 매번 네트워크로 다시 받지 않습니다.

## 검증 범위

자동 테스트 10개는 원본 파일 해시, 26개 페이지 구성, 하위 경로 URL, 상태 복제, 서로 다른 경기 로그의 CSV 해석·투타 기록·선수 카드·WAR·RE24·수비 OAA·기대 성적 결과를 확인합니다. 계산 결과는 원본 코드와 직접 비교합니다.

브라우저에서는 실제 611개 원본 파일 로딩(중복 처리 후 600경기), 26개 페이지의 초기 렌더링, 선수 선택 후 이동·뒤로가기·새로고침 복원, RE24 동적 필터 복원, 경기 전체 비활성화·목록 제거 후 새로고침, 소규모 그룹 재로딩을 점검했습니다.

직접 파일 선택 업로드는 브라우저 제어 도구의 파일 선택 대기 오류로 종단 검증을 완료하지 못했습니다. 파일 해석과 경기 추가는 자동 테스트로 확인했으나, 실제 파일 선택부터 페이지 이동까지의 흐름은 추가 확인이 필요합니다. 모든 하위 탭·내보내기 형식·드래그 조작 역시 전수 검증하지 않았습니다.

## 후속 개선 우선순위

1. 직접 파일 업로드·추가와 JSON/CSV/이미지 내보내기, 팀 빌더 드래그, 주요 하위 탭을 실제 브라우저에서 추가 검증합니다.
2. 큰 경기 범위에서 복원·재집계 비용을 측정한 뒤 파싱 결과 캐시나 Web Worker를 검토합니다.
3. 계산 함수와 화면 렌더링의 의존성을 더 나눠 페이지별 지연 로딩을 도입합니다.
4. 인라인 이벤트를 명시적인 이벤트 등록으로 옮기고 전역 호환 접근자를 점진적으로 제거합니다.
